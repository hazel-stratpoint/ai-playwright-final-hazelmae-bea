# Playwright + Cucumber Capstone: Study and Presentation Guide

This guide explains the automation project from its inputs through execution and reporting. It is written as a learning aid: follow the execution path first, then use the file-by-file sections to inspect the implementation.

## 1. What this project is

This repository is a browser-automation project built from:

- **Playwright** for launching browsers and automating pages.
- **Cucumber.js** for running human-readable Gherkin scenarios.
- **TypeScript** for typed step definitions, page objects, and utilities.
- **Page Object Model (POM)** to keep browser actions and assertions out of Gherkin and step bindings.
- **Winston** for structured console and file logs.
- **Cucumber HTML and Allure** for execution reports.

Cucumber is the test runner. This project does **not** use Playwright Test's `test()` runner, fixtures, or `playwright.config.ts`. `@playwright/test` is installed for Playwright browser APIs and its web-first `expect` assertions.

## 3. The execution flow: follow one step end to end

The most useful mental model is this chain:

```text
feature scenario
  -> Cucumber matches a sentence to a step definition
    -> step definition calls a PageManager page object
      -> page-object method reads a locator descriptor
        -> Playwright locates/interacts/asserts in the browser
  -> hooks create/close the scenario browser context and collect evidence
  -> Cucumber writes HTML and Allure results
```

For example, ST-003 says to increment the counter five times:

1. [`interactions.feature`](../features/interactions.feature) describes the business flow in Gherkin.
2. [`training-site.steps.ts`](../step-definitions/training-site.steps.ts) binds `I increment the counter {int} times` and delegates to the POM.
3. [`page.manager.ts`](../main/utils/page.manager.ts) lazily provides the training-site page object to the current scenario.
4. [`trainingSiteMethods.ts`](../main/functions/trainingSiteMethods.ts) clicks the increment locator five times and later asserts the displayed value.
5. [`trainingSiteLocators.ts`](../main/locators/trainingSiteLocators.ts) owns the selector `#counter-inc`.
6. [`world.ts`](../main/utils/world.ts) supplies the isolated Playwright `Page`.
7. [`hooks.ts`](../main/utils/hooks.ts) logs the scenario and tears down its context.
8. `cucumber.js`'s configured formatters produce the HTML and Allure result data.

If a scenario fails, the `After` hook in `hooks.ts` captures and attaches a screenshot before closing the context.

## 4. Setup and everyday commands

From a terminal:

```bash
cd ai-playwright-final
npm ci
npx playwright install chromium firefox webkit
cp .env.example .env
```

Edit `.env`:

```dotenv
BASE_URL=https://cdn.stratpoint.io/training-2026/playwright-training-site.html
BROWSER=chromium
```

`BASE_URL` selects the application under test. `BROWSER` selects one Playwright engine for that run. Supported values are `chromium`, `firefox`, and `webkit`. A browser binary needs to be installed for the selected engine. On Linux, `npx playwright install --with-deps chromium firefox webkit` also installs operating-system dependencies.

Useful checks and runs:

```bash
npm run typecheck             # compile/type-check TypeScript without emitting files
npm run test:dry-run          # check Gherkin discovery and step bindings; no browser scenario actions
npm run test:scaffold         # exercise framework wiring in the selected browser
npm run test:smoke            # ST-001–ST-010, activity Happy Path set
npm run test:regression       # ST-011–ST-015, activity Negative Path set
npm test                      # all 15 application cases, excludes scaffold/demo
npm run test:chromium         # full application suite in Chromium
npm run test:firefox          # full application suite in Firefox
npm run test:webkit           # full application suite in WebKit
```

The smoke and regression labels are how this capstone groups its cases. In some teams, “regression” means all tests that are rerun to detect regressions; follow the definitions in the project/activity you are working on.

The browser-specific scripts run sequentially, one engine per command. To try a subset in another engine, set `BROWSER=firefox` or `BROWSER=webkit` in `.env` and use the normal tag command. The provided commands reuse the same report paths, so each run replaces the Cucumber HTML report and the Allure result directory may contain results from more than one run unless cleared.

### Intentional failure screenshot demonstration

`features/demo-failure.feature` contains one deliberately failing case tagged `@demo-failure`. It expects the training site's initially hidden button to be visible. This is **not** a product defect or part of the 15 acceptance cases; it exists only to demonstrate the failure-evidence hook.

Run it explicitly:

```bash
npm run test:demo-failure
```

The command is expected to exit nonzero. The failure is considered a successful demonstration only if:

- the failure report shows the `@demo-failure` scenario as failed;
- a real image is written under `test-results/screenshots/`; and
- the screenshot is attached to the failed scenario in the Cucumber report.

Do not include this tag in ordinary suite commands. `cucumber.js` explicitly excludes it from `default`, `smoke`, and `regression` profiles. Use this command only when you want the demo failure evidence.

## 5. How the feature files are designed

Feature files live in `features/`, use `.feature`, and are parsed as Gherkin. The current application cases are grouped by area:

- [`authentication.feature`](../features/authentication.feature): login and registration.
- [`interactions.feature`](../features/interactions.feature): counter, visibility toggle, tabs, modal, and delayed content.
- [`data-display.feature`](../features/data-display.feature): table filtering and alerts.
- [`drag-and-frames.feature`](../features/drag-and-frames.feature): drag-and-drop and iframe input.
- [`demo-failure.feature`](../features/demo-failure.feature): isolated evidence-only failure.
- [`scaffold-check.feature`](../features/scaffold-check.feature): generic framework wiring check.

Gherkin keywords communicate intent:

- `Feature` groups related behavior.
- `Scenario` is one test case.
- `Given` describes the context/precondition.
- `When` describes an action.
- `Then` describes an observable outcome.
- `And` continues the previous kind of action/assertion.

Test IDs stay in scenario names, e.g. `[ST-001]`. This makes IDs visible in the report and preserves one source case to one scenario. Tags are separate metadata:

- `@smoke`: ST-001 through ST-010.
- `@regression`: ST-011 through ST-015 per this activity.
- `@scaffold`: generic framework check only.
- `@demo-failure`: opt-in screenshot-hook demonstration only.

Good feature files describe user-visible behavior, not CSS selectors, Playwright commands, TypeScript class names, or internal DOM structure. Keep a scenario focused, deterministic, and traceable to a test case or requirement.

## 6. How to add a test case yourself

Use this sequence whenever you add a case without relying on a generator.

### Step 1: Understand the source case

Identify its ID, goal, prerequisites, ordered actions, expected observable result, test data, and category/tag. Keep each case separate unless the requirements explicitly say otherwise. Clarify vague outcomes rather than inventing application behavior.

### Step 2: Write the Gherkin scenario

Add a scenario to the feature file for that application area. Preserve the source ID and keep the language readable to a tester or product stakeholder.

### Step 3: Bind each sentence

In `step-definitions/`, add or reuse a step definition whose Cucumber expression matches the feature sentence. Use `{string}` for quoted text and `{int}` for whole numbers. Step definitions should stay thin: get parameters and call a POM method. They should not contain CSS selectors, direct `page.click()` calls, sleeps, or business assertions.

### Step 4: Verify and record selectors

Inspect the permitted application under test. Prefer accessible locators such as `getByRole`, `getByLabel`, and `getByTestId`; use stable IDs if the app provides them. Put selector descriptors in a locator module rather than scattering strings across methods. Never invent a selector based only on a guess.

### Step 5: Implement a POM method

Add actions and assertions to `main/functions/<page>Methods.ts`. The method should have one clear responsibility, be named consistently, include a useful assertion for an expected result, and use the shared logger wrapper. Prefer Playwright's auto-waiting locator actions and web-first assertions over arbitrary sleeps.

### Step 6: Register the page when needed

If the page area does not already have a page object, add one lazy getter to `PageManager`. The scenario's custom World owns the page and the PageManager. Do not make static/global page objects shared between scenarios.

### Step 7: Tag and check the case

Use the source/activity's category, not assumptions. Run:

```bash
npm run typecheck
npm run test:dry-run
```

The dry-run checks that files load and Gherkin steps resolve. It does not prove that selectors or assertions work in a real browser. Run the requested scenario in the target browser(s) against an approved test environment.

## 7. Locators: what they are and how to judge them

A locator is a Playwright query that identifies one or more live elements. The locator module gives selectors a named home. In this project, `trainingSiteLocators` groups selectors by feature area (`login`, `registration`, `counter`, `table`, etc.); POM methods use these names rather than repeating selector strings.

Locator choice, from generally preferred to less preferred:

1. **Accessible role/name** when the page exposes the right semantics, such as a button named “Sign In”.
2. **Label or placeholder** for form fields when they are correctly associated and stable.
3. **Test ID** when the application provides a stable automation contract.
4. **Stable ID or CSS** when it reflects a real, verified app selector and is not overly structural.
5. **XPath** only when the DOM offers no better option; document why it is necessary.

This training site has stable IDs/test IDs, which is why the locators use them. For a production application, coordinate test IDs with developers and avoid selectors tied to styling classes or fragile DOM positions. Scope repeated names to their page/section or container. Assert a locator is unique when ambiguity could hide a defect.

Keep locators in one module per page/feature area, but do not create a generic “selector registry” so broad that ownership becomes unclear. A locator belongs to the POM that understands its meaning.

## 8. Page Object Model functions

[`trainingSiteMethods.ts`](../main/functions/trainingSiteMethods.ts) is the automation API used by step definitions. It combines:

- browser actions (fill, click, select, check, drag, iframe interaction);
- observable assertions (`toHaveText`, `toBeVisible`, `toHaveCount`, etc.);
- workflow-level behavior such as “sign in” or “filter the table”.

Its private `run_action` helper logs the action start, logs completion only after success, and logs/rethrows errors. Never catch an error and return a fake success value. Avoid putting all page behavior into one giant method; make each public method a readable action or assertion.

The current framework uses lowercase singular class names and `snake_case` POM methods for consistency with its existing scaffold. In a new codebase, follow that codebase's conventions rather than changing style mid-project.

Production-minded improvements to consider:

- Use specific domain types instead of broad strings for known sections and tabs.
- Keep test data out of method bodies when the same workflows need multiple data sets.
- Avoid logging passwords or personal data.
- Make environment-specific configuration explicit.
- Keep assertions aligned with user-visible requirements, not implementation details.
- Prefer deterministic setup and cleanup. Avoid dependencies between scenarios.

The training page is a static practice site. Its “login” and “registration” outcomes are client-side demo messages, not proof of real authentication, a persisted user account, or a backend transaction.

## 9. World, hooks, and lifecycle

[`world.ts`](../main/utils/world.ts) defines one custom Cucumber World per scenario. It stores the scenario's browser context, page, and lazily initialized PageManager. `start()` creates a fresh context/page; `dispose()` closes it and clears references.

[`hooks.ts`](../main/utils/hooks.ts) manages test-run and scenario lifecycle:

1. `BeforeAll` validates `BASE_URL` and `BROWSER`, then launches one selected browser process.
2. `Before` logs scenario start and asks the World to create an isolated context/page.
3. `After` captures/attaches a screenshot on failure before disposing the World.
4. `AfterAll` closes the shared browser process.

This pattern reuses an expensive browser process while keeping cookies, local storage, and page state isolated per scenario. If the suite later runs scenarios in parallel, revisit browser lifecycle and logger/report concurrency deliberately.

The browser selection uses the Playwright engines Chromium, Firefox, and WebKit. “Chromium” is not automatically the branded Google Chrome channel or Microsoft Edge. Browser-specific scripts select one engine per run.

## 10. PageManager and shared utilities

- [`page.manager.ts`](../main/utils/page.manager.ts) exposes lazy page-object getters. A POM is instantiated only when a step accesses it, and it receives that World’s page.
- [`logger.ts`](../main/utils/logger.ts) creates the Winston console/file logger and formats timestamped entries.
- [`screenshot.ts`](../main/utils/screenshot.ts) creates a sanitized filename, saves a full-page PNG under `test-results/screenshots/`, and returns the image buffer for Cucumber attachment.
- [`homePageMethods.ts`](../main/functions/homePageMethods.ts) is the generic scaffold POM; it validates and opens the configured URL and checks a generic page title.
- [`scaffold-check.steps.ts`](../step-definitions/scaffold-check.steps.ts) and `scaffold-check.feature` demonstrate framework wiring without claiming application-specific behavior.

Keep scenario state on the World, not in module-level variables. A process-level browser is acceptable when each scenario gets a fresh `BrowserContext`.

## 11. Configuration, dependencies, and reports

### TypeScript

[`tsconfig.json`](../tsconfig.json) enables strict type checking, targets Node 16 module semantics, and maps `main/*` imports to `./main/*`. This makes code such as `import { logger } from "main/utils/logger"` resolve consistently in TypeScript and at runtime using `tsconfig-paths/register`.

### Cucumber

[`cucumber.js`](../cucumber.js) centralizes common paths, TypeScript registration, hooks/step loading, and reporters. Profiles only alter selection:

- `default`: all application scenarios, excluding scaffold and intentional failure demo.
- `smoke`: `@smoke`, excluding scaffold/demo.
- `regression`: `@regression`, excluding scaffold/demo.
- `scaffold`: only `@scaffold`.
- `demo-failure`: only `@demo-failure`.
- `dry-run`: load all feature/step bindings with execution disabled.

Do not add a second runner for the same features. Ensure script names and profile definitions stay synchronized.

### Reports

- Cucumber report: `reports/cucumber-report.html`.
- Allure raw files: `allure-results/`.
- Allure HTML report: generated into `allure-report/`.
- Log: `logs/test-run.log`.
- Failure screenshot: `test-results/screenshots/`.

The HTML report is viewable by serving its folder:

```bash
npm run report:html:open
```

Allure's bundled command line is Allure 2 and requires Java:

```bash
npm run report:allure
npm run report:allure:open
```

If HTML or Allure output is used as evidence, identify which browser/run produced it. A report at a fixed path is overwritten by later Cucumber runs; save separate copies if the capstone requires results from multiple browsers.

## 12. Safety and scope

- The automation repository contains the test code; do not modify the application-under-test source.
- Do not run state-changing scenarios against real/shared production environments without authorization.
- Use synthetic/non-sensitive credentials and test data.
- Do not commit `.env`, secrets, `node_modules`, generated reports, logs, or screenshots unless explicitly requested.
- The demo-failure scenario is a deliberate exception for evidence practice. Explain that it is expected to fail and never present it as a failed acceptance case.
- Review `git status` before commits and stage only intended source/documentation files.

## 13. Production-readiness checklist

This is an educational capstone scaffold, not automatically a production-certified framework. Before using a similar framework in a real project, check:

- [ ] Supported Node and Playwright versions are pinned and documented.
- [ ] Browser versions are installed from the lockfile-compatible Playwright package.
- [ ] CI runs typecheck, dry-run, and selected browser suites with useful artifacts.
- [ ] Tags match an agreed test strategy, and test IDs map to requirements.
- [ ] Test data and environment are isolated and resettable.
- [ ] Credentials come from a secret manager and never enter logs/reports.
- [ ] Locators are accessible, stable, verified, and unique where required.
- [ ] Assertions verify business-visible outcomes and meaningful negative behavior.
- [ ] Tests are independent, repeatable, and safe to retry.
- [ ] Retries do not mask flakiness; flaky tests are investigated.
- [ ] Screenshots, traces, and logs are retained on failure with appropriate privacy controls.
- [ ] Parallel execution, report aggregation, and browser matrices have been intentionally configured.
- [ ] Accessibility, API, visual, and performance checks are handled by suitable tools rather than forced into UI scenarios.

## 14. Capstone presentation guide

### Suggested 6–8 minute walkthrough

1. **Problem and scope (30–45 sec):** Explain that the capstone automates 15 supplied scenarios against the training site using Playwright + TypeScript + Cucumber BDD.
2. **Architecture (1 min):** Show the execution chain: feature → step definition → PageManager/POM → locators → browser; mention Cucumber owns execution.
3. **One successful case (1–2 min):** Walk through ST-003 or ST-006 and trace its feature sentence to the thin step binding, named locator, and POM assertion.
4. **Cross-browser support (45 sec):** Show `BROWSER` and explain that `npm run test:chromium`, `test:firefox`, and `test:webkit` execute one engine per run. Mention the same app suite is intended to be portable, then show only browser results actually run.
5. **Evidence and failure handling (1 min):** Show the HTML report for the successful suite, then run `npm run test:demo-failure` to demonstrate a genuine failure and attached screenshot. State plainly that this one failure is intentional and excluded from regular suites.
6. **Engineering practices (1 min):** Point out scenario isolation in World/hooks, verified selectors in locator modules, web-first assertions, Winston logs, and report artifacts.
7. **Limitations / next steps (30 sec):** Clarify that training-site auth is simulated, Allure HTML needs Java, and CI/browser matrices or stronger data management are possible next steps.

### Live demo order and commands

Run these before presenting so network/browser issues do not consume presentation time:

```bash
npm run typecheck
npm run test:dry-run
npm run test:chromium
npm run test:firefox
npm run test:webkit
npm run test:demo-failure
npm run report:html:open
```

The last test command is expected to exit nonzero. Run it only after the clean passing suite if you want the final report to show the intentional failure. If you need both clean and demo reports, copy the first report to a clearly named evidence location before running the demo. Never edit report HTML to change test outcomes.

### What to say about results

- Give exact counts and browser names only for runs you actually completed.
- Separate the 15 application cases from the `@scaffold` wiring check and `@demo-failure` evidence case.
- Explain a failure by showing the assertion, screenshot, and report status—not by claiming the automation passed.
- If an engine was not run, say so. Browser support in configuration is not itself proof of a passing browser run.
- Identify generated reports as run evidence and retain their timestamps/context.

### Likely questions

**Why Cucumber and not Playwright Test?**  
The activity requires BDD/Gherkin. Cucumber executes the scenarios; Playwright supplies browser automation and assertions.

**Why have a POM?**  
It separates business-readable scenarios from UI mechanics and centralizes page-specific actions/assertions.

**Why isolate each scenario?**  
Fresh contexts prevent cookies, storage, and page state from leaking between cases.

**Why use an intentionally failing case?**  
It proves the failure hook captures and attaches a real screenshot. It is isolated and excluded from acceptance-suite profiles.

**Does the login test prove backend authentication?**  
No. The supplied site simulates login in the browser and displays a message; the case verifies that UI behavior only.

**Does a configured browser mean all browser tests passed?**  
No. Only completed run output demonstrates that. Report actual per-engine results.

## 15. Personal study plan

To learn the framework rather than memorize it:

1. Read one `.feature` scenario aloud and identify each Given/When/Then.
2. Find the exact step expressions in `training-site.steps.ts`.
3. Follow the called method into `trainingSiteMethods.ts`.
4. Find each selector in `trainingSiteLocators.ts`; inspect the training page to confirm it.
5. Trace `this.pages` back through PageManager and the custom World.
6. Read the `BeforeAll`, `Before`, `After`, and `AfterAll` hooks in order.
7. Run one tagged scenario, then inspect the log and report.
8. Run the isolated screenshot demo and confirm both file and report attachment.
9. Add a tiny practice scenario of your own and run typecheck/dry-run before browser execution.
10. Explain the flow without opening the generator prompts. If you can explain each boundary, you understand how to create and debug the framework manually.
